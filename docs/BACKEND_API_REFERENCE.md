# Backend API Reference (from FYP_BACKEND code, reviewed 2026-10-13)

Stack: ASP.NET Core (.NET 10), EF Core + SQL Server, JWT (HttpOnly cookie), Redis (OTP), MailKit (email), BCrypt.
Dev URLs: `http://localhost:5089`, `https://localhost:7259`. OpenAPI JSON (dev): `/openapi/v1.json`.

## Auth model
- Login sets cookie `accessToken` (HttpOnly, Secure, SameSite=Strict, 1 day). Token itself expires per `Jwt:ExpiryMinutes` (30).
- Token is **not** returned in the body → frontend must send requests with `credentials: 'include'` and be same-origin (use Vite dev proxy to the https backend).
- JWT claims: NameIdentifier=userId, Email, Role=RoleType.
- Errors come back as `{ message: string }` (forget-password 500s return a plain string).

## DB tables (FYP_DB/WorkforceManagementDB_Complete.sql)
User, Role, Employee, Employee_Status, Skills, Shift, Overtime, Organization, Organization_Manager, Contract, Workforce_Request, Employee_Allocation, Allocation_History, Organization_Reviews, Complaints, Reports. No seed data (roles e.g. "Admin", "Employee" must be inserted manually).

# Phase 4 APIs: Allocation, History, Availability (added 2026-10-13)

Uses only the existing allocation tables.
Admin allocations are always manual (is_allocated_by_AI = false). Rules: HARD (never overridable) = inactive employee, organization not active, organization without an active contract. CONTRACT rules (overridable with force = true; recorded as "[OVERRIDE]" in the history and as ALLOCATION_OVERRIDE in the audit log) = employee not Available/Idle, capacity (contract max_employees) exceeded, borrowing not allowed for a temporary allocation, employee busy (reallocate).
A failed rule check answers 409 { message, canOverride, violations: [{ code, message, overridable }] }.
Open allocation = actual_end_datetime IS NULL and status not in Completed / Reallocated / Cancelled / Released / Ended. Normal = owner org equals working org; Temporary = employee shared with another organization.

|---|---|---|

| GET | /api/admin/allocations/{id} | Details + history of the allocation |

| POST | /api/admin/allocations/{id}/reallocate | Move { assignOrgId, expectedEnd, reason, force } (old allocation ends as Reallocated) |

# Phase 5 APIs: Billing (added 2026-10-13)

Needs FYP_DB/migrations/005_billing.sql (Exchange_Rate, Payment_Rule + 5 built-in rules, Salary_Structure, Payroll_Run, Payroll_Item, Invoice, Invoice_Line, Invoice_Payment). Existing tables are not changed. Every amount is stored with its currency; payments and payroll lines also store the rate used to convert to PKR. Profit is never stored: collected (PKR) - payroll (PKR).
No exchange rate is invented: add USD -> PKR under Payment Rules -> Exchange rates (or pass exchangeRate when recording a payment).

Invoices: Draft -> Issued -> Paid, or Cancelled. Draft lines come from the contract rates and the allocated hours of the period: at any moment the first (contract min_employees) employees are billed at base_hourly_rate, anybody above that at extra_hourly_rate (hours are computed from Employee_Allocation intervals, clamped to the period, cancelled allocations ignored). Admin can add adjustment lines (minimum guarantee, discount) while Draft. Overdue / PartiallyPaid are worked out when reading.

## Input validation (frontend and backend)

The website checks every field while the person types (when a field is left, and on every change after that) and again on submit; the backend checks the same rules again.
- Names: letters, spaces and . ' - (2-100). Organization names: letters, numbers, spaces and & . , ' ( ) / - (2-150). Country: letters and spaces.
- Phone: digits, spaces and + - ( ), 7-15 digits (required for people and organizations). CNIC: 13 digits, stored as 12345-1234567-1.
- Email: valid address, max 150. Passwords: 8-100 characters, a letter and a number, no spaces.
- Numbers, dates and times: ranges, end after start, no future dates where they make no sense; currency codes are 3 capital letters; payment rule keys are CAPITAL_SNAKE_CASE (3-50).
- Custom attributes live in `FYP_BACKEND/fyp_project/Validation/ValidationAttributes.cs`; the browser rules in `FYP_FRONTEND/src/utils/validators.js` and the `useFormFields` hook.

## Contracts: no "sharing allowed"

A contract only says whether the organization may BORROW employees (borrowingAllowed, maxBorrowedEmployees). The "Sharing allowed" term was removed from the form, the details page, the DTOs and the models; the rule category "Sharing" is now "Borrowing". The old database columns (sharing_allowed, proposed_sharing_allowed) are left in place and unused.

## SLA module - removed

The SLA Monitor, recall requests, SLA violations, the SLA report, the contract "recall / response SLA" terms and the default recall setting were removed from the website, the backend and the database. To return an employee to the owner organization, reallocate them to it (or release them). Migration 004 was deleted and migration 010_remove_sla.sql drops the tables Recall_Request and SLA_Violation and the recall_sla / response_sla columns from databases that still have them.

## Queries (simplified)

Queries are raised by the organization side; the admin can only look at them and resolve them with a comment.
- GET `/api/admin/tickets?search&status(Open|Resolved)&organizationId&page&pageSize`, GET `summary` (open, resolved, averageResolutionHours), GET `{id}` (the query and its resolution; internal notes hidden)
- POST `/api/admin/tickets/{id}/resolve` `{comment}` (5+ characters) -> status Resolved, the comment saved as the resolution, audit TICKET_RESOLVED, and an email with the comment to the organization email and every active manager of that organization (QUERY_EMAIL_SENT / QUERY_EMAIL_FAILED in the audit log).
- Removed: creating a ticket, replies and internal notes, priority change, assigning, close / reopen. Old tickets that are InProgress count as Open and Closed ones as Resolved.
- For the future Organization Manager portal: a manager's notifications are the resolved tickets of the organizations they manage (`Ticket.org_id`, `status`, `resolved_at`, and the `Resolution` message in `Ticket_Message`).

Add query (for testing): POST `/api/admin/tickets` `{organizationId, subject, description, category?, priority?}` -> the query is created as Open with a TCK number (audit TICKET_CREATED). Shown as the "Add query" button on the Queries page.

## Notification bells: "Mark all as read" and alerts
Alerts (`alerts[]`: unread chat messages, contracts ending soon, "your shift starts at ...") are not audit entries, so the server cannot mark them as read. `NotificationBell.jsx` therefore counts `unreadCount - alerts.length` (unread audit entries, from the server's read marker) plus the alerts that were not yet marked as read in this browser. "Mark all as read" saves the server marker and remembers the current alerts in `localStorage` (`wfn-read-alerts-<userId>`). An alert counts again when its `key` changes (alert `key`, or its title when there is none): a new chat message, a different contract, or the next day's shift.

## Daily contracts (migration 015)
A contract whose **billing cycle is "Daily"** has its **minimum employees appointed every day**, inside the contract's daily start and end time. More employees come through **staff requests, on top of the minimum**, and the contract's maximum still limits the total. Run `FYP_DB/migrations/015_daily_contracts.sql` (adds `Employee_Allocation.daily_contract_id`; friend's DB needs 001-003, 005-015).

- **Contract rules** (`ContractLogic.Validate`): a Daily contract needs `minEmployees >= 1`, a `startTime` and an `endTime` (different; an end before the start means the window runs through the night). The other billing cycles are unchanged. Billing keeps working as before: the first `min` employees on duty are the base rate, anything above is the extra rate.
- **The appointment** (`Services/Workforce/DailyStaffingService.cs`): for every active Daily contract, the missing minimum is appointed from the free pool (active, no open allocation, Available or Idle). Order: people who worked this contract in the last days, then the organization's own employees, then (only if `borrowing_allowed`) others; best rating first. It uses the normal `AllocationService`, so every rule applies (maximum, active contract and organization). Each appointment has `expected_end = the window's end`, is marked with `daily_contract_id`, is written to `Allocation_History` and to the audit log (`EMPLOYEE_ALLOCATED`), so the employee's, the manager's and the admin's bells show it. When the window is over, the appointments are released automatically and appointed again the next day. Employees added through staff requests are not marked: they are the extra ones and are never released by this.
- **Time zone:** the contract times are read in the time zone chosen in Settings, or the server's own time zone when it is "this computer".
- **Automatic:** `DailyStaffingWorker` (hosted service) looks every 5 minutes: it ends finished appointments and appoints the missing minimum once the day's window has started. Running again only fills what is missing. A shortage (no free employee) is written once a day per contract as `DAILY_STAFFING_SHORT` (admin bell).

| Method | Path | What it does |
|---|---|---|
| GET | `/api/admin/daily-staffing?contractId=` | where each active daily contract stands today: `{ contractNumber, orgName, min, max, window, state (Complete / Short / Waiting / WindowEnded / NotStarted / Finished / OrganizationInactive / NoWindow), appointed, atOrganizationNow, extra, stillShort, employees[] }` |
| POST | `/api/admin/daily-staffing/run` | appoint the missing minimum of every daily contract now (also before the window starts) |
| POST | `/api/admin/daily-staffing/run/{contractId}` | the same for one contract |

Admin screens: the Billing cycle list has "Daily" (with a hint and the checks) in the contract form; an active daily contract shows a **Daily staffing** card on its details page (minimum, appointed today, extra from requests, missing, button "Appoint today's minimum now"); the Contracts page has "Appoint daily minimums".

## Changing an approved contract (migration 016)
Run `FYP_DB/migrations/016_contract_changes.sql` (extends `Contract_Modification_Request`: `requested_by_org_id`, `proposed_start_time`, `proposed_end_time`, `proposed_billing_cycle`, `effective_date`, `applied_at`; friend's DB needs 001-003, 005-016).

- The **organization** asks to change its **approved** contract. It may change: minimum / maximum employees, billing cycle, end date, daily start / end time, borrowing. **Never the hourly rates** (fixed; they are not even in the request). A reason is required (10-500 characters) and the change can start on a chosen day (`effectiveDate`, not in the past; empty = as soon as approved). Only what differs from the contract is stored. One change may wait at a time; the maximum cannot go below the employees working there now. **The current contract keeps running** while the admin decides.
- `POST /api/organization/contracts/{id}/changes` (ask), `POST /api/organization/contracts/changes/{modificationId}/withdraw` (take back a waiting one). `GET /api/organization/contracts/{id}` now also returns `canRequestChange`, `pendingChange` (current vs asked) and `changeHistory` (outcome, the admin's reply, when it started).
- **Notification:** the request is audited as `CONTRACT_MODIFICATION_REQUESTED` with the comment (admin bell and the organization manager's bell); the Contracts list shows "Change requested" (`hasPendingChange`).
- **Admin**, `Controllers/Admin/AdminContractChangesController.cs`: `GET /api/admin/contract-changes?contractId=&status=` (default Pending; `all`), `POST /{id}/approve` `{ note? }`, `POST /{id}/reject` `{ note }` (the reason is required). Screen: the "Changes asked by the organization" card on the contract details page.
- **Approve:** `ContractModificationService.ApplyAsync` saves a **new contract version** (the change reason is its summary; rates, priority and currency are kept) and mirrors it to the contract row, so everything that reads the contract follows: allocation limits, billing (base / extra employees), reports and the daily staffing (it runs for that contract right away). If it cannot be applied (for example more employees work there than the new maximum) nothing is saved and the admin is told. A change whose start day is later is **approved and waits**: the current terms keep running until that day, then the background worker (`DailyStaffingWorker`, every 5 minutes) puts it in force. Audit: `CONTRACT_MODIFICATION_APPROVED` / `_APPLIED`; the decision is also in `Approval_Decision` (`ContractModification`).

- **Public check:** `GET /api/verify/{invoice|receipt|payslip}/{number}?c=CODE` (no sign-in; the QR on every document opens `/verify/...`). The code is an HMAC of the document only the server can make. A payslip check never shows the name or the amount.
- **Announced payments** (organization -> manager -> admin): Organization `GET payable`, `GET|POST /api/organization/payments/submissions` (multipart: invoiceId, amount, method, reference, paidOn, note, file; the file is checked by content: JPG / PNG / WebP / PDF up to 5 MB, stored outside the web folder), `POST .../{id}/withdraw` (only while nobody decided). The amount cannot exceed the balance minus notices already waiting. Manager `/api/manager/billing/submissions` (`GET ?status`, `GET pending-count`, `POST {id}/verify`, `POST {id}/reject {reason}`). Admin `/api/admin/payment-submissions` (`GET ?status=Open|...|all`, `pending-count`, `POST {id}/approve {exchangeRate?, note?}`, `POST {id}/reject`). **Approving** goes through `PaymentService.RecordAsync` (the same code as "Record payment"): the payment is saved with its PKR value, the manager's verification is kept on it, the invoice becomes Paid when the balance is 0, and the receipt exists. Audit entries feed the bells (`PAYMENT_SUBMITTED`, `_VERIFIED`, `_APPROVED`, `_REJECTED`, `_WITHDRAWN`); the admin's and the manager's bell also show an alert with the number waiting.
- **Ledger** (`/api/admin/payments?search&organizationId&from&to&method&verified&page&pageSize` with totals per currency, `/export` up to 5000 rows for CSV).
- **Email a bill to the organization:** admin `POST /api/admin/invoices/{id}/email`, `.../reminder`, `POST /api/admin/payments/{id}/email` (receipt), `POST /api/admin/statements/email?orgId&from&to`; manager `POST /api/manager/billing/invoices/{id}/reminder`. Draft and cancelled invoices are never emailed.
- **Receivables (aging):** admin `GET /api/admin/reports/receivables?asOf` and manager `GET /api/manager/billing/receivables` - per organization and currency: not due, 1-30, 31-60, 61-90, over 90 days late, plus the late invoices.
- **Bank details for salaries:** employee `GET|PUT /api/employee/bank` (Settings > Bank details), admin `GET|PUT /api/admin/employees/{id}/bank` (card on the employee's page). The payroll sheet lists the bank details and warns about employees without them; a payslip shows only the end of the account number. `GET /api/employee/salary` months now carry `payslipItemId`.
- **Screens:** Admin > Payments, Payment Notices, Statements, Reports > Receivables, Settings > Billing, invoice / payroll pages (Print, Email, Reminder, Receipt, Salary slip, Payroll sheet); Manager > Payment Notices, Late Payments, Statements, invoice page (Print, Remind); Organization > Payments (tell us about a payment), Statements, invoice page (Print, I paid this, Receipt); Employee > My Salary (Salary slip), Settings > Bank details; Owner > Profit Statement. Documents print as an A4 page or an 80 mm slip (Print / Save as PDF).

## Pay online (demo payment gateway) (migration 022)

Run `FYP_DB/migrations/022_online_payments.sql` (`Online_Payment`). **The gateway is a DEMO: no real money moves.** Its checkout page (`/pay/demo/{token}`) is clearly marked, and the buttons Pay / Simulate a declined card / Cancel play the part of the gateway's confirmation.
- **Flow:** the organization chooses an invoice and an amount -> `POST /api/organization/payments/online { invoiceId, amount? }` makes a checkout (a secret token) and returns `checkoutPath` -> the browser goes to the gateway's page -> the gateway reports `paid` / `failed` / `cancelled` -> on `paid` the payment is recorded with `PaymentService` (the same code as every other payment): receipt, ledger, statement, bells (`INVOICE_PAYMENT_RECORDED`, `ONLINE_PAYMENT_FAILED`), receipt email, owner profit. A gateway payment is marked verified without a manager (the bank confirmed it); the method is "Online payment" and the reference is the gateway's. A repeated confirmation never pays twice.
- **Rules:** only the organization's own issued invoice; at most the balance minus what is already waiting (open payment notices and open checkouts reserve their amount); a checkout nobody finishes in 30 minutes expires; a foreign-currency invoice needs a stored exchange rate **before** the checkout starts; the admin can switch it off in Settings > Billing ("Allow paying online").
- **Endpoints:** `GET /api/organization/payments/online/options`, `POST .../online`, `GET .../online/{token}`, `GET .../online`; the demo gateway's side (no sign-in, the token is the key): `GET /api/gateway/demo/{token}`, `POST /api/gateway/demo/{token}/pay|fail|cancel`.
- **Real gateway later:** implement `IPaymentGateway` (`Name`, `IsDemo`, `CheckoutPath`) for JazzCash / Easypaisa / PayFast / Stripe, add its signed webhook that calls `OnlinePaymentService.CompleteAsync(token, "paid"|"failed"|"cancelled", gatewayReference)`, register it in `Program.cs` instead of `DemoPaymentGateway`, keep its keys in `appsettings.json` (never in git). `DemoGatewayController` answers 404 when the gateway is not the demo one. **Never leave the demo gateway enabled in a real deployment** - anybody with a checkout token could "pay" an invoice without paying.
- **Screens:** Organization > Payments (Pay online, I paid another way, Your online payments) and the invoice page (Pay online).
