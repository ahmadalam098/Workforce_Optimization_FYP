# Backend API Reference (from FYP_BACKEND code, reviewed 2026-10-13)

Stack: ASP.NET Core (.NET 10), EF Core + SQL Server, JWT (HttpOnly cookie), Redis (OTP), MailKit (email), BCrypt.
Dev URLs: `http://localhost:5089`, `https://localhost:7259`. OpenAPI JSON (dev): `/openapi/v1.json`.

## Auth model
- Login sets cookie `accessToken` (HttpOnly, Secure, SameSite=Strict, 1 day). Token itself expires per `Jwt:ExpiryMinutes` (30).
- Token is **not** returned in the body → frontend must send requests with `credentials: 'include'` and be same-origin (use Vite dev proxy to the https backend).
- JWT claims: NameIdentifier=userId, Email, Role=RoleType.
- Errors come back as `{ message: string }` (forget-password 500s return a plain string).

## DB tables (FYP_DB/WorkforceManagementDB_Complete.sql)
User, Role, Employee, Employee_Status, Skills, Shift, Overtime, Organization, Organization_Manager, Contract, Workforce_Request, Employee_Allocation, Allocation_History, Organization_Reviews, Complaints, Reports. No seed data (roles e.g. "Admin", "Employee" must be inserted manually).

# Phase 4 APIs: Allocation, History, Availability (added 2026-10-13)

Uses only the existing allocation tables.
Admin allocations are always manual (is_allocated_by_AI = false). Rules: HARD (never overridable) = inactive employee, organization not active, organization without an active contract. CONTRACT rules (overridable with force = true; recorded as "[OVERRIDE]" in the history and as ALLOCATION_OVERRIDE in the audit log) = employee not Available/Idle, capacity (contract max_employees) exceeded, borrowing not allowed for a temporary allocation, employee busy (reallocate).
A failed rule check answers 409 { message, canOverride, violations: [{ code, message, overridable }] }.
Open allocation = actual_end_datetime IS NULL and status not in Completed / Reallocated / Cancelled / Released / Ended. Normal = owner org equals working org; Temporary = employee shared with another organization.

|---|---|---|

| GET | /api/admin/allocations/{id} | Details + history of the allocation |
| GET | /api/admin/allocations/eligible-employees?search= | Active employees without an open allocation |

| POST | /api/admin/allocations/{id}/reallocate | Move { assignOrgId, expectedEnd, reason, force } (old allocation ends as Reallocated) |

# Phase 5 APIs: Billing (added 2026-10-13)

Needs FYP_DB/migrations/005_billing.sql (Exchange_Rate, Payment_Rule + 5 built-in rules, Salary_Structure, Payroll_Run, Payroll_Item, Invoice, Invoice_Line, Invoice_Payment). Existing tables are not changed. Every amount is stored with its currency; payments and payroll lines also store the rate used to convert to PKR. Profit is never stored: collected (PKR) - payroll (PKR).
No exchange rate is invented: add USD -> PKR under Payment Rules -> Exchange rates (or pass exchangeRate when recording a payment).

Invoices: Draft -> Issued -> Paid, or Cancelled. Draft lines come from the contract rates and the allocated hours of the period: at any moment the first (contract min_employees) employees are billed at base_hourly_rate, anybody above that at extra_hourly_rate (hours are computed from Employee_Allocation intervals, clamped to the period, cancelled allocations ignored). Admin can add adjustment lines (minimum guarantee, discount) while Draft. Overdue / PartiallyPaid are worked out when reading.

## Input validation (frontend and backend)

The website checks every field while the person types (when a field is left, and on every change after that) and again on submit; the backend checks the same rules again.
- Names: letters, spaces and . ' - (2-100). Organization names: letters, numbers, spaces and & . , ' ( ) / - (2-150). Country: letters and spaces.
- Phone: digits, spaces and + - ( ), 7-15 digits (required for people and organizations). CNIC: 13 digits, stored as 12345-1234567-1.
- Email: valid address, max 150. Passwords: 8-100 characters, a letter and a number, no spaces.
- Numbers, dates and times: ranges, end after start, no future dates where they make no sense; currency codes are 3 capital letters; payment rule keys are CAPITAL_SNAKE_CASE (3-50).
- Custom attributes live in `FYP_BACKEND/fyp_project/Validation/ValidationAttributes.cs`; the browser rules in `FYP_FRONTEND/src/utils/validators.js` and the `useFormFields` hook.

## Contracts: no "sharing allowed"

A contract only says whether the organization may BORROW employees (borrowingAllowed, maxBorrowedEmployees). The "Sharing allowed" term was removed from the form, the details page, the DTOs and the models; the rule category "Sharing" is now "Borrowing". The old database columns (sharing_allowed, proposed_sharing_allowed) are left in place and unused.

## SLA module - removed

The SLA Monitor, recall requests, SLA violations, the SLA report, the contract "recall / response SLA" terms and the default recall setting were removed from the website, the backend and the database. To return an employee to the owner organization, reallocate them to it (or release them). Migration 004 was deleted and migration 010_remove_sla.sql drops the tables Recall_Request and SLA_Violation and the recall_sla / response_sla columns from databases that still have them.

## Queries (simplified)

Queries are raised by the organization side; the admin can only look at them and resolve them with a comment.
- GET `/api/admin/tickets?search&status(Open|Resolved)&organizationId&page&pageSize`, GET `summary` (open, resolved, averageResolutionHours), GET `{id}` (the query and its resolution; internal notes hidden)
- POST `/api/admin/tickets/{id}/resolve` `{comment}` (5+ characters) -> status Resolved, the comment saved as the resolution, audit TICKET_RESOLVED, and an email with the comment to the organization email and every active manager of that organization (QUERY_EMAIL_SENT / QUERY_EMAIL_FAILED in the audit log).
- Removed: creating a ticket, replies and internal notes, priority change, assigning, close / reopen. Old tickets that are InProgress count as Open and Closed ones as Resolved.
- For the future Organization Manager portal: a manager's notifications are the resolved tickets of the organizations they manage (`Ticket.org_id`, `status`, `resolved_at`, and the `Resolution` message in `Ticket_Message`).

Add query (for testing): POST `/api/admin/tickets` `{organizationId, subject, description, category?, priority?}` -> the query is created as Open with a TCK number (audit TICKET_CREATED). Shown as the "Add query" button on the Queries page.

### Employees: monthly salary instead of hourly rate

### Organization Manager handles employees' queries; severe ones go to the admin (no new migration)
An employee's query is a `Ticket` with `source = "Employee"` and `raised_by_user_id` = the employee's user. Its `org_id` is the organization the employee works for (open allocation), otherwise their home organization, so a borrowed employee's queries go to the manager of the organization they work for. **Severe = priority High or Critical.**
- `GET /api/manager/tickets` now also returns every query of the manager's employees (any category), plus `source`, `raisedBy`, `isSevere`, `canResolve`, `canForward`; new filters `source=Employee|Organization` and `severe=true`; severe ones sort first.
- `GET /api/manager/tickets/summary` adds `openEmployeeQueries` and `severeToSend`.

- `POST /api/manager/tickets/{id}/resolve` `{ comment }` - the manager answers an employee's query that is **not** severe and not yet sent to the admin (409 for a severe one: "Send it to the admin"; 404 for an organization's own ticket, which the admin answers). Saved as the Resolution message, audit `TICKET_RESOLVED`, and the employee is emailed the answer.
- `POST /api/manager/tickets/{id}/forward` `{ note?, priority? }` - send to the admin; `priority` lets the manager set the severity (the change is written in the audit entry the admin sees in the bell). After sending, only the admin resolves it.
- `POST /api/manager/tickets` accepts `employeeId` instead of `organizationId` to log an employee's query for them (403 for an employee who does not work for the manager's organizations).
- Admin: `POST /api/admin/tickets/{id}/resolve` on an employee's query now also emails the employee, not only the organization and its managers.

### Organization Manager: staff requests and manual staffing (the fallback when the AI allocation does not work; no new migration)
The manager sees the staff requests of their organizations (like the admin does) and staffs an **approved** request by hand from the employee pool, with the same AllocationService rules as the admin (approved organization, active contract, capacity, borrowing, availability). A broken rule always blocks: the manager gets no override. The admin still approves or rejects a request.
- `GET /api/manager/requests/summary` -> `{ waitingForAdmin, approvedShort, fullyStaffed, rejected }`
- `GET /api/manager/requests?search&status=Pending|Approved|Rejected|Cancelled|Unstaffed&priority&orgId&page&pageSize` (Unstaffed = approved but still short; those and pending ones sort first)
- `GET /api/manager/requests/{id}` - staffing numbers (`requiredEmployees`, `staffedNow`, `stillNeeded`), the contract's min/max employees and borrowing, warnings, allocations, the admin's decision notes, `canStaff` (approved and still short). 404 for another organization's request.
- `GET /api/manager/requests/{id}/candidates?search` - the free active employees (no open allocation), best fit first: has the requested skill, available, same home organization, rating; with `matchesSkill`, `isBorrowed`, `skills`.
- `POST /api/manager/requests/{id}/staff` `{ employeeIds: [...] }` - allocates each to the request (planned end = the request's end); returns per-employee results with the reason for any refusal (already allocated, not available, request full, contract capacity ...). 409 for a request that is not approved. Audited as EMPLOYEE_ALLOCATED with the manager as actor.
- `POST /api/manager/requests` `{ organizationId, requiredEmployees, skillId?, priority, startDatetime, endDatetime, reason }` - the manager logs a request for one of their organizations (same checks as the admin form: approved organization with an active contract, at most 100 employees and 90 days, end in the future); it is Pending until the admin decides; audit WORKFORCE_REQUEST_CREATED (shows in the admin's bell). To remove an allocated employee the existing `POST /api/manager/allocations/{allocationId}/release` is used.
- Frontend: `/manager/requests` and `/manager/requests/:id` ("Staff Requests" in the sidebar), with a "New request" button.

#### Update: the manager can allocate to a request that still waits for the admin
- `POST /api/manager/requests/{id}/staff` now also accepts a **Pending** request: the first successful allocation approves it (a review "Approved by the organization manager when staffing it." is recorded, audit `WORKFORCE_REQUEST_APPROVED`, the organization is emailed). If nobody could be allocated, the request stays Pending and no approval is recorded. Rejected or cancelled requests still refuse.
- `GET /api/manager/requests` items and `GET /api/manager/requests/{id}` return `canStaff` (pending or approved, and still short) and, in the details, `willApprove`.
- Frontend: an **Allocate** button on each row of `/manager/requests` opens the list of free employees (best fit first); tick the ones to send to the organization.

## Organization Manager - notifications (bell)

`ManagerOnly`. Same read marker table (`Notification_State`) as the admin bell; the first call marks everything older as already seen.

| Method | Path | What it does |
|---|---|---|
| GET | `/api/manager/notifications?limit=20` | `{ enabled, unreadCount, alerts: [{ title, message, link }], items: [{ id, action, title, message, actorName, entityType, entityId, createdAt, isUnread }] }` |
| POST | `/api/manager/notifications/read-all` | Marks everything as read |

Items come from `Audit_Log` and are limited to what concerns the manager: their organizations (not the email log), contracts, staff requests, allocations, invoices (issued / cancelled / payment recorded), queries and complaints (created / resolved / forwarded), their employees (updated, activated, skills, shifts, overtime), payroll that includes their employees, and notices about their own account. Their own actions are not shown. Alerts: unread chat messages from organizations, and contracts ending within `NOTIFY_CONTRACT_EXPIRY_DAYS`. Returns `enabled: false` when `NOTIFY_INAPP` is off.
